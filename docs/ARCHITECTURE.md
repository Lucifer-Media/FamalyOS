# Family OS — Архитектура (Итерация 1)

## Стек

| Слой | Технология | Почему |
|---|---|---|
| Backend | NestJS + TypeScript | Модульность, DI, guard'ы для RBAC из коробки, зрелая экосистема |
| ORM/БД | Prisma + PostgreSQL 16 | JSONB для специализированных полей, надёжные транзакции, зрелые миграции, полнотекстовый поиск «из коробки» |
| Frontend | Next.js (App Router) + Tailwind | SSR/SPA-гибрид, единая типизация с backend через общие DTO, быстрая адаптивная вёрстка |
| Файлы | Локальный storage backend с абстракцией | Явный контракт `save/read`, чтобы позже подставить S3-совместимое хранилище без изменения бизнес-логики |
| Аутентификация | JWT (access+refresh) + TOTP 2FA | Простая горизонтальная модель, обязательная 2FA по требованиям проекта |

Стек выбран самостоятельно (агентом) по критерию «надёжнее и быстрее работает» — так и было прямо согласовано с заказчиком.

## Принцип «оболочка + специализация»

Ядро Итерации 1 — таблица `entities`: общая оболочка (id, владелец, тип, заголовок, статус,
уровень конфиденциальности, версия) + JSONB-поле `attributes` для специфики конкретного типа.

```
Entity (оболочка)
 ├── entityType = 'knowledge_article'  → attributes: { content, folder, tags }
 ├── entityType = 'passport'           → (Итерация 2, тот же движок)
 ├── entityType = 'computer'           → (Итерация 2, тот же движок)
 └── entityType = 'medical_record'     → (Итерация 2, тот же движок)
```

Все типы бесплатно получают:
- версионирование (`entity_versions`) по модели Git — откат создаёт новую версию;
- связи с любыми другими сущностями (`entity_links`) — основа «графа жизненного контекста»;
- привязку файлов (`entity_files`);
- права доступа через `PermissionResource`, к которому привязан `entityType`;
- полнотекстовый поиск (GIN-индекс по `searchText`, конфигурация `russian`).

Итерация 1 реализует ОДИН конкретный тип (`knowledge_article` — семейная база знаний) как
доказательство того, что паттерн действительно работает end-to-end, не деля пример на бумаге
и код в разных мирах. Паспорт/СНИЛС/компьютер/медзаключение (Итерация 2) добавляются как новые
`entityType` + запись в `ENTITY_TYPE_RESOURCE` (см. `entities.service.ts`), без изменения ядра.

## Модель прав доступа (RBAC)

Два уровня:
1. **Ролевая матрица по умолчанию** (`src/common/permissions.ts`) — статическая таблица
   роль × ресурс × действие.
2. **Точечные исключения** (`MembershipPermissionOverride`) — например, гостю разрешили
   просмотр медицины для конкретного членства. Имеют приоритет над матрицей.

Ресурсы: `GENERAL, DOCUMENTS, FINANCE, MEDICAL, CONFIDENTIAL, INTEGRATIONS, USERS,
KNOWLEDGE_BASE, FILES`. Действия: `VIEW, CREATE, EDIT, ARCHIVE, MANAGE`.

Дополнительно: запись с `confidentialityLevel = STRICTLY_CONFIDENTIAL` требует права
`CONFIDENTIAL:VIEW` независимо от прав на сам ресурс — двойной барьер для самых чувствительных
данных (аналог мед. записей с особым статусом).

## Версионирование (модель Git)

```
v1 (CREATE) → v2 (UPDATE) → v3 (UPDATE) → revert к v1
                                              ↓
                                    v4 (REVERT, снимок v1, revertedFromVersion=1)
```

Откат никогда не удаляет `entity_versions` — он лишь добавляет новую запись со старым
состоянием. `EntityVersion.snapshot` хранит полное состояние сущности на момент версии.

## Запрет физического удаления

Ни один API-эндпоинт Итерации 1 не выполняет `DELETE` над пользовательскими данными.
Вместо этого везде используется `RecordStatus`: `ACTIVE → ARCHIVED → VOID`.
Исключение — `MembershipPermissionOverride`/`Session` (технические/служебные записи, не
пользовательские данные) допускают обычные обновления без версионирования.

## Аудит vs версии сущностей — зачем два журнала

- `entity_versions` — история **содержимого** конкретной сущности (что было раньше, откат).
- `audit_logs` — история **действий** (кто, когда, что сделал, включая вход, смену прав,
  скачивание файла) — более широкий security-журнал, не привязанный к одной сущности.

Оба неизменяемы (append-only), но решают разные задачи.

## Инварианты (не менять без пересмотра миграций!)

- `src/common/enums.ts` должен буквально совпадать с enum'ами `prisma/schema.prisma`.
  Модуль существует, чтобы чистую бизнес-логику (`permissions.ts`) можно было
  юнит-тестировать без поднятого Prisma Client — при любом изменении enum'а в схеме
  обязательно обновите и этот файл.
- Любое новое поле в `attributes` (JSONB) специализированного типа не требует миграции БД —
  но требует обновления DTO соответствующего контроллера (валидация на входе).
