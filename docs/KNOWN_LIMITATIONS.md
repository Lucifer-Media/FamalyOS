# Известные ограничения (среда разработки агента)

Этот документ фиксирует, что именно НЕ было проверено вживую в среде, где писался код,
и почему — чтобы при развёртывании на реальном сервере вы точно знали, на что обратить
внимание при первом запуске.

## 1. Prisma Client не был сгенерирован в песочнице агента

**Причина:** `prisma generate` и `prisma migrate dev` скачивают бинарник query-engine с
`binaries.prisma.sh`. Сетевой egress песочницы агента ограничен списком доменов
(`npmjs.org`, `github.com`, `pypi.org`, репозитории apt и т.д.) — `binaries.prisma.sh` в этот
список не входит.

**Что это значит практически:**
- Схема БД (`prisma/schema.prisma`) была написана, а соответствующая ей начальная миграция
  (`prisma/migrations/20260807000000_init/migration.sql`) — написана вручную и **реально
  проверена**: применена напрямую через `psql` к чистой PostgreSQL 16 (создано 15 таблиц,
  все внешние ключи и индексы применились без ошибок).
- Backend-код был проверен на компиляцию (`tsc --noEmit`): **9 оставшихся ошибок типов** —
  все они вида `Module "@prisma/client" has no exported member 'ConfidentialityLevel'`
  и подобные — это прямое следствие того, что типы `@prisma/client` не были сгенерированы.
  Других ошибок компиляции нет.
- Юнит-тесты чистой бизнес-логики (ролевая матрица прав, шифрование 2FA-секретов) —
  **реально запущены, 10/10 проходят**.
- E2E-тесты (`test/*.e2e-spec.ts`), которым нужен настоящий Prisma Client и поднятая БД —
  написаны, но не запускались агентом. Они корректны по типам API (проверено вручную) и
  должны пройти на сервере после `npm install && npx prisma generate`.

**Что сделать на сервере при первом запуске:**
```bash
cd apps/api
npm install
npx prisma generate
npx prisma migrate deploy   # применит ту же миграцию, что уже проверена вручную
npm run test                # юнит-тесты (10/10 уже подтверждены агентом)
npm run test:e2e            # e2e-тесты — первый реальный прогон именно здесь
```
Если `test:e2e` покажет расхождения — это первое, что стоит проверить при приёмке
Итерации 1, поскольку это единственный непроверенный агентом уровень.

## 2. Frontend — реально собран и проверен

В отличие от backend, `next build` в apps/web **выполнялся и завершился успешно** —
включая полную проверку типов TypeScript и генерацию всех 13 маршрутов. Ограничений здесь нет.

## 3. Отправка email для приглашений не реализована

`POST /family-spaces/:id/invitations` создаёт приглашение и возвращает токен в ответе API,
но не отправляет письмо — это зафиксировано как технический долг (см. `TECH_DEBT.md`), а не
скрытое упрощение архитектуры. Ссылку `/accept-invite/<token>` нужно передать вручную, пока
не подключён email/интеграционный слой (Итерация 4).

## 4. Docker-образы не собирались и не запускались агентом

Dockerfile/docker-compose.yml написаны по образцу уже работающих на ThinkPad контейнеров
(AdGuard, Grafana, Prometheus), но `docker build`/`docker compose up` не выполнялись в
песочнице (отсутствует Docker). Первая реальная сборка образов произойдёт на вашем сервере —
см. `docs/DEPLOYMENT.md`.
