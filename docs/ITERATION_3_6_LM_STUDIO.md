# Family OS — Итерация 3.6 (поддержка LM Studio / OpenAI-совместимых локальных LLM)

## Что сделано

Раньше `OllamaService` умел говорить только с нативным API Ollama
(`/api/generate`, один `prompt`). LM Studio отдаёт OpenAI-совместимый API
(`/v1/chat/completions`, массив `messages`, ответ в
`choices[0].message.content`) — другой формат запроса и ответа.

Класс **не переименован** (остался `OllamaService`) — чтобы не трогать три
места, которые на него ссылаются (`ai-chat.service.ts`,
`ocr.processor.ts`, `ai-assistant.module.ts`), но внутри он теперь умеет
оба формата, провайдер выбирается переменной окружения. Публичный
интерфейс (`isConfigured()`, `chat()`, `extractFields()`) не изменился —
ни `AiChatService`, ни `ocr.processor.ts` трогать не пришлось.

## Как включить LM Studio

В `.env` на сервере (рядом с `docker-compose.yml`, `/opt/family-os/.env`):

```bash
LLM_PROVIDER=openai_compatible
LLM_URL=http://100.71.172.64:1234
LLM_MODEL=qwen/qwen3.6-35b-a3b
```

Если основной адрес (Tailscale) недоступен, есть резерв — по вашей же
подсказке про локальный IP:

```bash
LLM_FALLBACK_URL=http://192.168.1.12:1234
```

`LLM_API_KEY` не нужен — LM Studio по умолчанию не требует авторизации;
если у вас всё же включена, добавьте `LLM_API_KEY=...` — он уйдёт как
`Authorization: Bearer <ключ>`.

После правки `.env`:
```bash
cd /opt/family-os
docker compose up -d --force-recreate api
```
(пересобирать образ не нужно — это просто переменные окружения).

**Важно про сеть**: контейнер `api` должен дотягиваться до
`100.71.172.64:1234` — обычно исходящий трафик из контейнера идёт через
хост с NAT, и раз Tailscale настроен на самом ThinkPad, это должно
работать "из коробки". Если будут таймауты — проверьте прямо из
контейнера:
```bash
docker compose exec api curl -s http://100.71.172.64:1234/v1/models
```
Если и это не отвечает — дело не в Family OS, а в сетевой связности
контейнер→Tailscale-пир, тогда резервный `LLM_FALLBACK_URL` (локальный IP)
и правда пригодится.

## Обратная совместимость

Если у вас уже был настроен Ollama через старые переменные (`OLLAMA_URL`,
`OLLAMA_MODEL`, `OLLAMA_FALLBACK_URL`, `OLLAMA_TIMEOUT_MS`) — они
продолжают работать как есть, ничего менять не нужно. Новые `LLM_*` имена
— это просто более общие имена для той же настройки (раньше подразумевали
только Ollama, теперь — любой провайдер), с приоритетом: если задано и
`LLM_URL`, и `OLLAMA_URL` — используется `LLM_URL`.

## Найденный и исправленный побочный баг

При обобщении кода для docker-compose добавлены новые переменные вида
`LLM_URL: ${LLM_URL:-}` — но Docker Compose при отсутствии переменной в
`.env` передаёт в контейнер **пустую строку**, а не отсутствие переменной.
Оператор `??` пустую строку не считает "нет значения" — конструкция
`process.env.LLM_URL ?? process.env.OLLAMA_URL` в этом случае вернула бы
`""` и молча сломала бы фолбэк на `OLLAMA_URL` для всех, у кого уже
настроен Ollama по старым переменным, как только они обновятся до этой
версии. Исправлено функцией `firstNonEmpty()`, которая явно трактует
пустую строку как "не задано". Отдельный регрессионный тест на этот
случай — `ollama-lmstudio.spec.ts`.

Также по пути исправлена утечка таймера: при сетевой ошибке (не
HTTP-ошибке, а, например, ECONNREFUSED/таймауте) `clearTimeout()`
раньше не вызывался — таймер повисал до `timeoutMs` вхолостую. Не влияло
на корректность ответов, но могло держать процесс/тесты "живыми" дольше
нужного.
